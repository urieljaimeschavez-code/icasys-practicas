ICASYS · Conectar Supabase

Conectar ICASYS con Supabase

Versión 3.0 preparada el 26 de octubre de 2026.

Estado actual

Actualización del 1 de noviembre de 2026: la conexión real fue verificada, DB_DRIVER se cambió a postgres y se importaron las 3 cuentas y 1 estancia locales. Storage permanece privado. Consulta ESTADO_ACTUAL.md. La aplicación todavía se ejecuta localmente y no ha sido publicada. Los pasos siguientes se conservan como guía para una nueva instalación; no deben repetirse sobre la base que ya tiene usuarios.

Las pruebas de SQL emulado no certifican TLS, políticas, bloqueos ni permisos del proyecto real. Esas comprobaciones son parte de la conexión y aceptación posteriores.

1 Crear el proyecto

En https://supabase.com/ crea tu cuenta e inicia sesión personalmente. Crea un proyecto nuevo llamado icasys-practicas con el plan gratuito. Selecciona la organización de tu cuenta y una región adecuada. Define y conserva la contraseña de la base de datos de forma privada. Espera a que termine de prepararse.

No es necesario comprar un dominio ni introducir datos de pago para esta configuración del proyecto gratuito. Si la plataforma ofrece un plan de pago o te solicita un compromiso adicional, revisa la opción elegida antes de continuar.

2 Crear tablas y depósito privado

En SQL Editor ejecuta, en orden, el contenido de estos archivos del proyecto:

  1. supabase/01-schema.sql
  2. supabase/02-storage.sql

El primero crea el esquema privado icasys con usuarios, estancias, actividades, metadatos de evidencias, revisiones, sesiones, intentos de acceso, auditoría y diario de cargas. No crea cuentas de aplicación ni contiene contraseñas. Al consultar tablas desde Table Editor, selecciona el esquema icasys en lugar de public.

El segundo crea el depósito icasys-evidencias, marcado como privado, con límite de 2 MB y los tipos permitidos. No crea políticas de acceso público. Si el depósito ya existía no cambia su configuración; el diagnóstico verificará que sea privado.

No agregues icasys a los esquemas expuestos por Data API. No concedas lectura de las tablas a anon ni authenticated. Los usuarios de nuestra aplicación no son usuarios de Supabase Auth: se conserva el ingreso existente de Node.js con contraseñas derivadas y roles propios. No se crea un segundo sistema de autenticación.

3 Configurar credenciales solo en el servidor

Copia .env.example como .env en la raíz del proyecto. Este archivo está excluido del control de versiones y de las rutas públicas. Llénalo personalmente, sin pegar credenciales en el chat ni en capturas:

DB_DRIVER=postgres
DATABASE_URL=postgresql://USUARIO:CONTRASENA@HOST:5432/postgres
PG_CA_FILE=C:/ruta/privada/certificado-raiz.crt
SUPABASE_URL=https://REFERENCIA.supabase.co
SUPABASE_SERVICE_ROLE_KEY=CLAVE_PRIVADA_SERVICE_ROLE
SUPABASE_STORAGE_BUCKET=icasys-evidencias
PORT=4173
HOST=127.0.0.1
APP_ORIGIN=http://127.0.0.1:4173
COOKIE_SECURE=0

DATABASE_URL: en el botón Connect del proyecto copia la conexión de Session pooler, normalmente en puerto 5432. Es adecuada para este servidor Node persistente y puede funcionar desde redes IPv4. Copia el usuario y host exactos que muestre tu proyecto. Sustituye la contraseña localmente; si contiene símbolos reservados, codifícala para una URL. No uses la URL de Data API en este campo.

PG_CA_FILE: descarga el certificado raíz de la base desde la configuración SSL del proyecto si el certificado no está en las autoridades confiables del runtime. La ruta debe existir en el equipo que ejecuta Node; en el servicio publicado será otra ruta. No se desactiva la validación TLS ni se usa rejectUnauthorized:false. El controlador retira parámetros sslmode de la URL para que no reemplacen la configuración de validación.

SUPABASE_URL: origen HTTPS del proyecto, sin rutas. SUPABASE_SERVICE_ROLE_KEY: clave privada legacy service_role del proyecto para Storage; no es anon ni publishable. Solo el servidor la utiliza, después de autorizar cada solicitud. La clave tiene privilegios elevados y no debe agregarse a app.js, index.html, repositorios ni variables públicas. Si se usa una clave secreta de formato diferente, debe verificarse compatibilidad con Storage antes de cambiar el tipo documentado.

Si aún no tienes estos valores, conserva DB_DRIVER=sqlite. No uses credenciales ficticias como si la migración ya estuviera conectada.

4 Instalar y comprobar

En otro equipo instala Node.js 24 y ejecuta npm install. En este equipo las dependencias ya se instalaron con pnpm y existe un archivo de bloqueo pnpm-lock.yaml. Para reproducir las versiones exactas usa pnpm install --frozen-lockfile.

Ejecuta:

npm run cloud:check

Debe confirmar conexión PostgreSQL con validación TLS, tablas presentes y depósito privado. El diagnóstico no imprime claves ni cadenas de conexión. Si falla, revisa archivo .env, estado del proyecto, contraseña, certificado y scripts SQL. No desactives TLS para resolverlo.

5 Elegir una inicialización

Elige una de estas opciones en una base de destino vacía. No se sobrescriben usuarios existentes.

Conservar registros locales

Primero respalda la instalación SQLite y detén las escrituras durante la copia. La importación lee el archivo local sin modificarlo. Luego ejecuta:

npm run cloud:import

Copia usuarios y hashes de contraseña, estancias, actividades, revisiones y archivos al depósito privado. Las contraseñas actuales siguen funcionando. No copia sesiones ni intentos de acceso. La auditoría anterior permanece en el respaldo local y se registra un evento de importación en la nube. No borres el respaldo.

La importación sube archivos antes de confirmar los registros SQL. Si una carga o transacción falla, no presenta éxito; las cargas quedan registradas en storage_uploads para revisión. No se borran automáticamente documentos. Antes de reintentar revisa la causa y el destino.

Crear una instalación nueva

Si no deseas copiar datos locales:

npm run cloud:init

Crea las tres cuentas iniciales y una estancia de evaluación. Las contraseñas temporales se guardan en data/accesos-nube.txt, nunca en pantalla pública. Cada titular debe cambiarlas personalmente al ingresar. No ejecutes este comando si vas a usar cloud:import.

6 Iniciar y probar

Inicia con INICIAR.cmd o npm start. La terminal debe indicar Motor: postgres. Si falla la nube no cambia silenciosamente a SQLite.

Prueba acceso con los tres perfiles, cambio de contraseña, registro, corrección, aprobación, descarga de evidencias y reportes. Consulta las filas en Supabase y confirma que las evidencias no sean accesibles mediante una URL pública. Reinicia Node y verifica que se conserven los datos.

Comando de auditoría de cargas sin confirmación:

npm run cloud:storage-audit

Es de solo lectura y no elimina objetos. Al reemplazar una evidencia se conserva el objeto privado anterior hasta una limpieza controlada; puede ocupar cuota adicional. La tabla evidence apunta únicamente al archivo actual. El diario detecta cargas sin confirmación, no todos los objetos históricos reemplazados.

7 Respaldos en nube

El comando npm run backup corresponde a SQLite y no debe confundirse con un respaldo Supabase. En nube hay dos componentes separados: PostgreSQL y Storage. Un volcado de las tablas no incluye los bytes de los archivos.

Define un procedimiento de copia PostgreSQL con pg_dump o las herramientas admitidas por el plan contratado y una copia independiente de los archivos privados. Prueba la restauración en otro proyecto antes de confiar en el procedimiento. No se han configurado respaldos automáticos ni se afirma que el plan gratuito los incluya. El archivo local SQLite conservado permite recuperar el punto previo a la migración, no la actividad posterior en nube.

8 Publicar la aplicación posteriormente

La base de datos en nube no publica por sí sola la interfaz Node. Para que los asesores entren desde otros equipos falta alojar el servidor en un servicio compatible y configurar sus secretos. Se incluye un Dockerfile como preparación; no se ha construido ni desplegado una imagen en esta etapa.

En ese servicio utiliza HOST=0.0.0.0, COOKIE_SECURE=1 y APP_ORIGIN con la dirección HTTPS exacta del sitio. El puerto será el que asigne el proveedor. Conserva DATABASE_URL y la clave privada solo en las variables secretas del servidor. La conexión PostgreSQL valida el certificado. No ejecutes la app con .env dentro de una imagen pública.

Arquitectura de la versión preparada

Navegador → Servidor Node.js → PostgreSQL Supabase (esquema icasys)
                       └──→ Storage Supabase (depósito privado)

Las evidencias se descargan a través de nuestra API, que comprueba la cuenta y estancia y verifica su SHA-256. No se devuelve una URL pública ni la clave de servicio al navegador.

ICASYS · Manual de usuario

Manual de usuario

Sistema de seguimiento de prácticas profesionales · ICASYS
Versión 2.0 · 18 de octubre de 2026 · Entorno local de evaluación

1. Para qué sirve

El sistema centraliza actividades, horas, evidencias y revisiones de una estancia profesional. Cada usuario ingresa con su propia cuenta. Las horas pendientes y las horas aprobadas se muestran por separado. Solo una aprobación del asesor asignado suma al avance.

2. Ingresar por primera vez

  1. Inicia el servidor con INICIAR.cmd y deja la ventana abierta.
  2. Abre http://127.0.0.1:4173 en tu navegador.
  3. Ingresa el correo y la contraseña temporal entregados por el administrador.
  4. La primera vez se solicitará cambiar la contraseña. Escribe la temporal, una nueva y su confirmación.
  5. La nueva contraseña debe tener entre 12 y 128 caracteres, mayúscula, minúscula y número. No uses la misma contraseña temporal.
  6. Al guardar, se abrirá tu portal. Si no tienes una estancia asignada, aparecerá un mensaje para solicitarla al administrador.

Las cuentas iniciales son admin@icasys.local, asesor@icasys.local y practicante@icasys.local. Sus contraseñas se generan individualmente en data/accesos-iniciales.txt al primer inicio. No son cuentas de correo reales ni cuentas del sitio de ICASYS.

3. Elementos comunes

  • Inicio: resumen de la estancia, horas y avance.
  • Mis prácticas / Revisar actividades: bitácora con búsqueda por título y filtro de estado.
  • Mis reportes: resumen por estancia y exportaciones.
  • Mi cuenta: permite cambiar tu contraseña. Esto cierra las otras sesiones de tu cuenta.
  • Actualizar datos: consulta los últimos cambios del servidor, por ejemplo después de que tu asesor apruebe una entrega.
  • Cerrar sesión: invalida la sesión actual. Para probar otro perfil, cierra e inicia con otra cuenta.

Una sesión dura hasta ocho horas. En un equipo compartido utiliza Cerrar sesión al terminar. Las pestañas del mismo navegador comparten sesión: para pruebas simultáneas usa navegadores o perfiles separados.

4. Administrador

4.1 Crear una cuenta

En Usuarios, pulsa Crear usuario. Captura nombre, correo, perfil y contraseña temporal. El correo debe ser único. Entrega la contraseña al titular por un medio privado. El usuario tendrá que cambiarla al primer ingreso.

Los perfiles son Practicante, Asesor y Administrador. El rol no se cambia desde la edición para evitar que las asignaciones existentes pierdan consistencia. Para un nuevo rol crea una cuenta con correo distinto y revisa las asignaciones.

4.2 Editar o desactivar

En Usuarios, pulsa Editar. Puedes modificar nombre, correo y estado. Si capturas una nueva contraseña temporal, la anterior deja de funcionar y se cierran las sesiones del titular. El sistema no muestra contraseñas actuales.

Desactivar una cuenta bloquea nuevos ingresos y cierra sesiones existentes. El historial no se elimina. No puedes desactivar tu propia cuenta.

4.3 Registrar una estancia

  1. Crea primero la cuenta del practicante y la del asesor, ambas activas.
  2. En Gestionar estancias, pulsa Nueva estancia.
  3. Selecciona al practicante y al asesor por sus cuentas.
  4. Captura institución educativa, proyecto, fechas y horas requeridas.
  5. Guarda la estancia. Al iniciar sesión, el practicante la encontrará en su portal y el asesor en su lista de asignaciones.

Las horas requeridas pueden estar entre 1 y 2000 en incrementos de media hora. El periodo debe ser válido. Cuando ya existen actividades, no se puede cambiar al titular ni excluir sus fechas al editar el periodo. Se puede reasignar el asesor; las revisiones anteriores conservan el nombre de quien las realizó.

4.4 Consultar historial

Historial del sistema muestra los últimos 200 eventos: ingresos, cambios de contraseña, gestión de usuarios, estancias y actividades. Las fechas de auditoría están en UTC, identificadas en la tabla. No se registran contraseñas ni el contenido de archivos en el historial.

5. Practicante

5.1 Registrar una actividad

  1. Abre Mis prácticas y, si tienes varias estancias propias, selecciona la correcta.
  2. Pulsa Registrar actividad.
  3. Captura nombre, fecha, horas y descripción. Explica el trabajo y el resultado.
  4. Opcionalmente adjunta un PDF, PNG, JPG o TXT de hasta 2 MB.
  5. Guarda un borrador para continuar después o pulsa Enviar al asesor.

La descripción requiere entre 15 y 3000 caracteres. Cada actividad acepta entre 0.5 y 12 horas en incrementos de media hora. La fecha debe pertenecer al periodo de tu estancia y no puede ser futura. La suma de actividades enviadas del mismo día y estancia no puede superar 12 horas. Los borradores no suman al avance ni son visibles para el asesor.

5.2 Estados

Estado Qué significa Qué puedes hacer
Borrador Todavía no se entrega Editar y enviar
En revisión Entregada al asesor Consultar y esperar revisión
Corrección El asesor solicita ajustes Leer comentario, editar y reenviar
Aprobada Horas validadas Consultar y descargar evidencia

No se editan actividades en revisión ni aprobadas. Esta regla evita modificar una entrega después de su revisión.

5.3 Atender una corrección

Abre Ver detalle de la actividad con estado Corrección. Lee el historial, pulsa Editar y reenviar, modifica lo solicitado y envía. Puedes conservar la evidencia anterior sin seleccionar otro archivo; elegir uno nuevo la reemplaza. Las horas se sumarán solo después de aprobarse.

El historial conserva decisiones y comentarios, pero no guarda copias completas de cada versión del texto o archivo. No se ofrece eliminación de actividades en esta versión.

6. Asesor

Solo aparecen las estancias asignadas a tu cuenta y las actividades entregadas de esos practicantes.

  1. Abre Revisar actividades y selecciona la estancia.
  2. Filtra En revisión y pulsa Revisar.
  3. Lee descripción, horas e historial. Descarga la evidencia si existe.
  4. Para aprobar, agrega un comentario opcional y pulsa Aprobar horas.
  5. Para solicitar cambios, escribe una indicación de al menos 10 caracteres y pulsa Solicitar corrección.

Una actividad aprobada deja de estar pendiente; pulsar nuevamente desde una pestaña desactualizada no duplicará las horas. Si recibes un aviso de versión modificada, cierra el detalle, actualiza los datos y revisa otra vez.

7. Reportes

En Mis reportes se muestran nombre del practicante, proyecto, asesor, periodo, horas aprobadas, horas en revisión, meta y avance. El porcentaje se redondea al entero más cercano y su indicador se limita a 100%; las horas aprobadas siguen mostrándose completas.

  • Descargar CSV produce una tabla para Excel y otros programas. Si Excel no separa columnas, usa Datos → Desde texto/CSV y selecciona UTF-8 y delimitador coma.
  • Imprimir / PDF abre la función de impresión del navegador. Selecciona Guardar como PDF. El formato impreso oculta la navegación del portal.

El reporte es de seguimiento y no sustituye una constancia oficial ni incluye firma electrónica.

8. Problemas frecuentes

Mensaje o situación Acción
El navegador rechaza la conexión Ejecuta INICIAR.cmd y revisa la dirección y el puerto
Correo o contraseña incorrectos Revisa la cuenta; pide restablecimiento al administrador si es necesario
Demasiados intentos Espera 15 minutos; no sigas intentando contraseñas
Sin estancia asignada Pide al administrador que registre la asignación correcta
No aparecen horas nuevas Pulsa Actualizar datos; comprueba que estén aprobadas
Archivo rechazado Revisa tamaño, extensión y contenido real del archivo
La actividad cambió Actualiza datos antes de volver a editar o revisar
Sesión vencida Inicia sesión nuevamente

La información ahora se guarda en el servidor: limpiar el navegador no elimina actividades. La carpeta data del servidor sí debe conservarse y respaldarse.

ICASYS · Instalación y operación

Manual de instalación y operación

Versión 2.0 · Entorno validado: Windows y Node.js 24.19.0

Requisitos

  • Node.js 24.x (el proyecto utiliza el módulo integrado node:sqlite; no se garantiza compatibilidad con otras versiones).
  • Navegador moderno con cookies habilitadas.
  • Permiso de lectura y escritura en la carpeta del proyecto y data.
  • Puerto local 4173 disponible. No se requiere instalar dependencias npm.

Node.js 24 incorpora node:sqlite, que puede mostrar avisos experimentales según su versión. Se mantiene el runtime validado como requisito del proyecto; una actualización debe pasar de nuevo las pruebas.

Instalación en este equipo

La carpeta es C:\Users\Lenovo\OneDrive\Documentos\ChatGPT\Proyecto ICASIS.

Haz doble clic en INICIAR.cmd. El archivo utiliza primero el runtime disponible en el perfil del usuario; si no existe, intenta usar node del PATH. Mantén su terminal abierta y entra a http://127.0.0.1:4173.

Si ya hay una instancia ejecutándose en segundo plano, la nueva indicará que el puerto está en uso. No inicies un segundo servidor para la misma base. No detengas procesos de Node sin comprobar que pertenecen a este proyecto.

Instalación en otro equipo

  1. Instala Node.js 24 desde su sitio oficial.
  2. Copia el código del proyecto. Para una instalación nueva no copies data ni accesos de otra persona.
  3. Abre una terminal en la carpeta y ejecuta:
node --version
npm start

En el primer arranque se crea data/icasys.sqlite, el esquema y las tres cuentas iniciales. Las contraseñas aleatorias están en data/accesos-iniciales.txt. Cambia cada contraseña al ingresar; conserva el archivo solo mientras se entregan los accesos y retíralo después de manera controlada. El servidor nunca publica ese archivo.

Configuración

Variable Predeterminado Uso
PORT 4173 Puerto HTTP local
DATA_DIR carpeta data del proyecto Ubicación de la base y configuración inicial
COOKIE_SECURE sin activar Con valor 1 exige envío de cookie por HTTPS

Ejemplo de evaluación en otro puerto:

$env:PORT = '4180'
node server.cjs

La aplicación escucha exclusivamente en 127.0.0.1. No está expuesta a Internet ni a la red local. El modo HTTPS requiere un proxy o infraestructura de despliegue y no forma parte del arranque local. No actives COOKIE_SECURE en una demostración HTTP, porque el navegador puede impedir que funcione la sesión.

Arranque y parada

Si ejecutaste desde terminal, Ctrl + C detiene el servidor. Antes de reiniciar confirma que no haya formularios en envío. Los datos se conservan. Si el servidor fue iniciado en segundo plano por una herramienta, identifica su proceso y ruta antes de detener únicamente esa instancia.

Respaldo

Ejecuta desde la carpeta del proyecto:

npm run backup

El respaldo consistente se guarda en data/respaldos/icasys-FECHA.sqlite. Incluye usuarios, hashes de contraseña, sesiones, estancias, actividades, evidencias, revisiones y auditoría. No se limita a copiar el archivo principal mientras hay escrituras: usa la API de respaldo de SQLite.

Los respaldos son privados. Guarda una copia protegida fuera de la computadora y prueba su restauración periódicamente. La frecuencia y retención deben acordarse con el responsable; se propone un respaldo por jornada de uso y antes de cambios al sistema. No se configuraron automatizaciones.

Restauración controlada

  1. Detén el servidor y confirma que nadie está trabajando.
  2. Conserva la carpeta data actual con otro nombre o una copia en una ubicación protegida. No la borres.
  3. Crea una nueva carpeta data-restaurada y coloca el respaldo con nombre icasys.sqlite dentro de ella.
  4. Inicia apuntando DATA_DIR a la nueva carpeta, sin superponer archivos -wal o -shm de otra base:
$env:DATA_DIR = 'C:\ruta\del\proyecto\data-restaurada'
node server.cjs
  1. Verifica ingreso, estancias, actividades y descarga de evidencias. Los accesos serán los vigentes al momento del respaldo; usa una contraseña conocida de esa fecha.
  2. Para un incidente de seguridad invalida sesiones del respaldo antes de reanudar acceso y aplica restablecimientos con el responsable técnico.

No hay recuperación automática por correo. Un administrador activo puede restablecer la cuenta desde Usuarios. Si se pierde el acceso a todos los administradores, corresponde una intervención técnica controlada y respaldada; no se elimina la base para recrear accesos.

Pruebas y actualización

Ejecuta npm test antes de entregar una actualización. Las pruebas crean sus propias bases en tests/tmp-* y no usan la información del usuario. La primera versión del esquema está en lib/schema.sql y PRAGMA user_version=1. ICASYS · Manual técnico

Manual técnico

Sistema de seguimiento de prácticas profesionales ICASYS · Versión 2.0

1. Decisión tecnológica

Se eligió Node.js 24 porque la interfaz existente ya estaba construida en JavaScript y puede conservarse, el residente conoce esta tecnología y el entorno disponible permite ejecutar el sistema sin instalar dependencias adicionales. Se utiliza SQLite como motor relacional real, con claves foráneas, restricciones, índices, transacciones y persistencia en disco.

SQLite simplifica la instalación y el traslado para la evaluación académica. No se eligió por afirmar que sustituye cualquier infraestructura institucional: si aumenta significativamente el uso concurrente se deberá evaluar PostgreSQL o MySQL y adaptar la capa de persistencia. Las llamadas síncronas de SQLite son una limitación de escalabilidad del diseño actual. El transporte HTTP y el enrutamiento están implementados con módulos estándar de Node, sin framework externo.

Fuentes técnicas: https://nodejs.org/docs/latest-v24.x/api/sqlite.html y https://nodejs.org/docs/latest-v24.x/api/crypto.html. La implementación y las pruebas se ejecutaron con Node.js 24.19.0; los detalles de la API deben contrastarse con esa rama al mantener el proyecto.

2. Arquitectura

El navegador no contiene las contraseñas ni decide los permisos efectivos. app.js presenta los datos autorizados y realiza solicitudes a la API. server.cjs autentica, comprueba el rol y la asignación de la estancia, valida y ejecuta consultas parametrizadas. lib contiene persistencia, autenticación y validadores reutilizables. El modelo SQL está separado en lib/schema.sql.

Crear / editar actividades Propias; edición solo borrador/corrección No No
Aprobar / pedir corrección No Solo asignadas y en revisión No

La interfaz solo muestra opciones de su perfil, pero la barrera real está en el servidor. Alterar JavaScript o enviar IDs de otras estancias no concede autorización. Una cuenta inactiva pierde acceso y sus sesiones quedan revocadas. El administrador no aprueba horas: se mantiene la revisión con el asesor responsable.

4. Autenticación

  • Correo único sin distinción entre mayúsculas y minúsculas.
  • Contraseñas entre 12 y 128 caracteres con mayúscula, minúscula y número.
  • Derivación mediante scrypt, sal aleatoria de 16 bytes y resultado de 64 bytes. La base guarda sal y derivación, nunca la contraseña recuperable.
  • Comprobación con timingSafeEqual. Se deriva una contraseña ficticia también cuando la cuenta no existe.
  • Token de sesión aleatorio de 32 bytes; SQLite guarda únicamente su hash SHA-256. Cookie HttpOnly, SameSite=Strict, Path=/ y duración máxima de ocho horas.
  • COOKIE_SECURE=1 permite añadir Secure para una instalación HTTPS. La evaluación local utiliza HTTP en loopback.
  • Token CSRF por sesión y validación de Origin para escrituras. No se habilita CORS.
  • Diez intentos fallidos bloquean durante 15 minutos por origen de conexión y correo. Los contadores se conservan en base de datos.
  • Al cambiar o restablecer contraseña se revocan las sesiones anteriores. El cambio de contraseña crea una sesión nueva.
  • Contraseña inicial temporal obligatoria. Sin completarla solo se permiten consulta de sesión, cambio de contraseña y salida.

Las sesiones comparten cookie entre pestañas del mismo navegador y origen. No hay acceso simultáneo a tres perfiles mediante un selector. Se debe cerrar sesión o utilizar perfiles de navegador separados.

5. Reglas de actividades

Una actividad admite título de 1 a 120 caracteres, descripción de 15 a 3000, horas de 0.5 a 12 en pasos de 0.5 y fecha válida dentro de la estancia, no futura según America/Mexico_City. Las actividades enviadas de la misma estancia y fecha no superan 12 horas acumuladas; borradores no entran en ese cálculo. Estas reglas son propuestas de operación que ICASYS debe validar.

El campo version aumenta al modificar o revisar. Las solicitudes de actualización incluyen la versión consultada; una discrepancia responde 409 para evitar sobrescribir otra edición o revisar dos veces la misma entrega. Las escrituras y su auditoría se ejecutan en transacciones.

El avance es ROUND(horas aprobadas / meta × 100), limitado visualmente a 100%. Las horas reales no se recortan. Revisar dos veces no duplica registros de horas: el total se deriva de actividades con estado approved, no de sumas manuales acumuladas.

6. Evidencias y reportes

La carga utiliza JSON con contenido Base64 y un máximo de solicitud de 3 MB. Se limita cada archivo a 2 MB. Se valida nombre, extensión y firma básica de PDF, PNG y JPG, o texto UTF-8 sin bytes nulos para TXT. Esto no equivale a un análisis antivirus. Se almacena BLOB, MIME, tamaño y SHA-256 en evidence. La descarga pasa por autenticación y autorización, utiliza Content-Disposition: attachment y X-Content-Type-Options: nosniff.

Reemplazar una evidencia conserva únicamente la versión actual del archivo. El historial guarda decisiones y comentarios, no instantáneas de todos los textos o archivos anteriores. No hay eliminación de actividades en la interfaz.

CSV e impresión se generan en el navegador con los datos autorizados recibidos del servidor. CSV escapa comillas y prefija apóstrofo cuando una celda comienza con =, +, @ o -, para evitar la interpretación directa como fórmula. El PDF se obtiene con la impresión del navegador, no mediante un generador de documentos del servidor. No se incluyen firmas o validez oficial.

7. API

Todas las rutas devuelven JSON salvo la descarga de evidencias. Las escrituras utilizan Content-Type: application/json, Origin del mismo servidor y X-CSRF-Token (excepto login, que no exige token CSRF pero sí Origin). Los ejemplos describen estructura, no contienen contraseñas reales.

8. Operación y mantenimiento

El servidor expone index.html, app.js, styles.css, el logotipo y el expediente de documentación por una lista explícita. Código de servidor, bases, respaldos y accesos no se publican. Respuestas no se cachean. Se incluyen CSP y protección contra enmarcado; la política permite el estilo en línea usado por la interfaz y las fuentes externas de Google Fonts.

Las claves foráneas están activas y SQLite usa WAL y busy_timeout. Las evidencias están dentro de la misma base para que el respaldo capture un expediente completo. backup.cjs usa la API de respaldo de SQLite; no basta copiar un archivo activo ignorando el WAL.

Limitaciones conocidas: sin recuperación de contraseña por correo, MFA, verificación de correo, notificaciones, antivirus, auditoría externa inmutable, pruebas de alta carga o despliegue público. SQLite y scrypt usan operaciones síncronas en algunos caminos; se debe evaluar su desempeño antes de aumentar la escala. El archivo de base de datos no está cifrado en reposo. El control de acceso del sistema operativo y la protección de respaldos son parte de la operación.

Integridad y respaldo

PRAGMA foreign_keys=ON, journal_mode=WAL y busy_timeout=5000. Las operaciones compuestas se ejecutan con BEGIN IMMEDIATE / COMMIT o ROLLBACK. El esquema utiliza consultas preparadas y no concatena entradas de usuario en SQL. Las reglas que dependen del usuario, fecha o suma diaria se verifican en el servidor.

El esquema está principalmente normalizado: identidad en users, asignaciones en placements, hechos de trabajo en activities y revisiones separadas. El nombre del asesor y practicante se obtiene mediante JOIN, sin duplicarlo en cada actividad. Las evidencias actuales no tienen versionado histórico.

Resumen

El proyecto desarrolla una aplicación web independiente para registrar y dar seguimiento a estancias de prácticas profesionales. Incluye cuentas individuales de practicante, asesor y administrador, asignación de estancias, bitácora de actividades, evidencias, revisión, cálculo de horas aprobadas y reportes. El sistema utiliza Node.js y SQLite, conserva una identidad visual basada en el portal ICASYS y funciona localmente para su evaluación. La integración al sitio institucional constituye una etapa posterior sujeta a aprobación y revisión de infraestructura.

Planteamiento del problema

Se propone centralizar el seguimiento de actividades y horas de practicantes en un expediente accesible según responsabilidades. Sin un registro unificado de entregas y revisiones puede resultar difícil identificar qué actividades están pendientes, qué horas fueron validadas y cuáles requieren corrección.

Lo anterior representa la necesidad que aborda la propuesta, no un diagnóstico confirmado de los procesos internos de ICASYS. Deben documentarse entrevistas con responsables, herramientas utilizadas actualmente, dificultades observadas y reglas operativas para sustentar el problema final. No se afirma que la organización carezca de otro sistema sin haberlo validado.

Justificación

Un expediente por estancia permite relacionar actividades, evidencias y decisiones del asesor, separar horas pendientes de aprobadas y generar un reporte consistente. Las cuentas individuales y la autorización en servidor sustituyen el cambio libre de perfiles del primer prototipo. La base de datos permite persistencia independiente del navegador y respaldos del expediente.

Para la formación del residente, el proyecto integra análisis de requerimientos, diseño de datos, desarrollo de interfaz y servidor, autenticación, pruebas y documentación. La utilidad institucional deberá evaluarse con los responsables y usuarios previstos.

Objetivo general

Desarrollar y validar en un entorno de evaluación un sistema web con autenticación y base de datos para gestionar estancias profesionales, registrar actividades y evidencias, revisar entregas y consultar el avance de horas de los practicantes de ICASYS.

Marco técnico

La arquitectura cliente-servidor separa presentación de validación y persistencia. Node.js procesa solicitudes HTTP; SQLite conserva entidades relacionadas mediante claves foráneas y transacciones. Se utilizan consultas parametrizadas, contraseñas derivadas con sal, sesiones en cookie HttpOnly, control CSRF y autorización por asignación. El avance se calcula a partir de actividades aprobadas para evitar acumulaciones duplicadas.

Las decisiones detalladas, fuentes de documentación oficial y limitaciones están en MANUAL_TECNICO.md. El modelo entidad-relación y diccionario se encuentran en BASE_DE_DATOS.md.

Metodología de desarrollo

Se siguió un desarrollo incremental: revisión visual del portal de referencia, definición del módulo de prácticas profesionales, construcción de una maqueta navegable, prueba de su flujo con el usuario y evolución a un sistema con persistencia y autenticación. La fase actual agrega controles en servidor, modelo SQL y pruebas de integración.

Para el informe académico debe complementarse cada fase con fechas reales, decisiones revisadas por asesores y evidencias de trabajo. No se declara una metodología institucional específica ni ceremonias que no se realizaron.

Resultados verificables

El conjunto automatizado ejecutado reportó 13 pruebas aprobadas y ninguna fallida, incluyendo control de acceso, corrección y aprobación, evidencias restringidas, persistencia tras reapertura y respaldo de datos. La pantalla de acceso fue revisada visualmente. No se midieron mejoras porcentuales en productividad, tiempos administrativos ni satisfacción de usuarios; esas métricas requieren evaluación real.
